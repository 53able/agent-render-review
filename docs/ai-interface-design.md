# AIインターフェース設計／レビュー: Render Director

## 1. 結論

- 判定: 設計案（動作するプロトタイプあり。ユーザー調査・専門監査は未実施）
- 主要判断: vork の「エージェントが書く→描画→見る→直す」ループに人間の演出者を入れる。0.2.0 では ADE モードを追加した。ADE（Claude Code、Codex など）のエージェントが MCP 経由でシーンを提案し、描画画像を自分で見る。人間は Director で比較し、指差しでフィードバックし、採否を決める。採用した画像とシーンはプロジェクトへ書き戻す。差分はモデルの説明ではなくシーンJSONから計算する。
- 最大リスク: 承認の境界は、同じユーザー権限で動くエージェントへの強制力を持たない。ADE のエージェントはファイルや `.vork/` の状態を直接書けるため、人間の採否を経ずに画像を置くことを技術的に防げない。manifest もエージェントが書けるので改ざんの証明にならない。強制が必要ならADE側のサンドボックスと組み合わせる。

## 3. リスク階層

| 操作 | 階層 | 可逆性 | 影響 | 必要な制御 |
|---|---|---|---|---|
| シーン閲覧、版の切替、比較 | R0 | 即時 | なし | 自動 |
| previs/draft 描画（版ディレクトリ内へ出力） | R0 | 即時（再生成可） | 数秒のGPU時間 | 自動。実行中表示と中止 |
| エージェントへの提案依頼 | R1 | 即時（提案は別版、HEAD不変） | API費用、送信される文脈 | 送信文脈を事前に表示・除外可。中止可 |
| 提案の採用（HEAD変更） | R1 | 即時（旧版をHEADへ戻せる） | 以後の作業の基準 | 差分確認後の明示操作 |
| 直接編集（色、粗さ、発光、光量） | R1 | 即時（新しい版として保存） | なし | 自動。版として記録 |
| final 描画 | R2 | 条件付き（ファイル上書きあり） | GPU時間（重いシーンで長時間）、既存final置換 | 操作直前承認。承認はシーンハッシュに束縛、10分で失効 |
| ローカルアセット参照（.glb、画像のみ） | R2 | 条件付き | ローカルファイル読取 | 提案内で警告表示し、採否を人間が判断 |
| カスタムSlangプログラム、`.gltf`（外部バッファURIを検査できない） | R2 | 条件付き | 長時間コンパイル、GPUストール、`#include` 等によるファイル読取の可能性 | プロトタイプでは禁止（モデル外のポリシーで遮断） |
| 絶対パス・`..`・URLのアセット参照、ダウンロード | R3 | 不可逆（情報流出、ライセンス違反の可能性） | 機密ファイル読取、権利不明素材の混入 | 禁止（モデル外のポリシーで遮断） |
| プロジェクトへの書き戻し（`<assetDir>/<slug>.png`、`.vork/adopted/<slug>.json`） | R2 | 条件付き（上書きは元に戻せない。git管理下なら復元可） | 開発中アプリの見た目が変わる | エージェントは依頼だけ。人間がDirectorで直前承認。承認はシーンハッシュに束縛、10分で失効。書き込み直前にパスを再検査 |
| ページプレビュー（開発中ページを headless Chrome で開き、画像要求だけ差し替える） | R0 | 即時 | プロジェクトのファイルは変えない。ページの読み込みで開発サーバーへ要求が出る | 自動。URLとパターンは config.json で人間が設定 |
| 外部公開・送信 | R3 | 不可逆 | 公開 | 機能を持たない（対象外） |

## 5. 主要な設計判断

### D-01: 指差しで対象を指定する

- 対象状態: 入力
- 変更前または現状: vork は対象をノード名やJSONパスで指定する。演出者は名前を知らない。
- 提案: 描画時に object_index チャネルを同時出力し、サーバーで16bit PNGを復号してブラウザへ渡す。ホバーで名前と輪郭、クリックで選択。選択は「SELECTED objects」として明示的に文脈へ入る。
- 根拠: 暗黙の文脈（どれのことか）を直接操作へ移し、自然文の曖昧さを減らす。
- トレードオフ: ライトとカメラは画像に写らないため、一覧からしか選べない。インスタンス単位の選択は未対応。
- 受入条件: ホバーで正しいノード名が出る。キーボードだけで同じ選択ができる。
- 未検証事項: 細い物体や密集物で狙った対象を選べるか。

### D-02: 差分はデータから計算し、モデルの説明と突き合わせる

- 対象状態: 出力
- 変更前または現状: エージェントは変更内容を自然文で説明する。説明が実際の変更と一致する保証はない。
- 提案: 親版と提案版のシーンJSONをノード名単位で比較し、フィールドごとの before/after を表で出す。モデルの `claimed_changes` と照合し、未言及の変更と、主張したが変わっていない項目に警告を付ける。
- 根拠: 流暢な説明を正しさの証拠にしない。外部から確認できる証拠（差分、vorkの露出統計、画像）を優先する。
- トレードオフ: 表が長くなる。フィールド名はJSON語彙のまま。
- 受入条件: 自己テストで既知の2変更だけが検出される。シーン直下の `render` 変更も主張と照合される。
- 未検証事項: 利用者が警告に気づき判断を変えるか。

### D-03: 提案は版であり、HEADを動かさない

- 対象状態: 出力、行動
- 変更前または現状: vork の素朴なループではエージェントがシーンファイルを直接上書きする。
- 提案: 提案ごとに新しい版を作り、`proposed` 状態で保持する。採用でHEADを移し、破棄は打ち消し線で残す。直接編集も版になる。過去の採用版はHEADへ戻せる。
- 根拠: 確率的な出力は再試行で同じ結果に戻らない。分岐と比較で回復できるようにする。
- トレードオフ: 版が増える。版の削除と命名は未実装。
- 受入条件: 破棄後に親版へ戻り、HEADが変わらない。
- 未検証事項: 長いセッションで版一覧を辿れるか。

### D-04: エージェントにはツールを渡さない（単独モード）

- 適用範囲: 単独モードの内蔵エージェント。ADEモードではエージェントはMCPツールだけを持ち、採否・承認のツールは持たない（D-07）。

- 対象状態: 構成、計算
- 変更前または現状: vork README はエージェントにCLIを直接操作させる前提。
- 提案: `claude -p --tools "" --strict-mcp-config --setting-sources ""` で起動し、JSONスキーマ準拠の提案だけを受け取る。描画、ファイル書込、承認はサーバーが行う。提案はサーバー側ポリシー（ファイル参照の絶対パス・`..`・URL・許可外拡張子、カスタムプログラム、全 `resolution` の各成分上限、名前重複）を通過しないとvorkへ渡らない。直接編集も値の型と範囲を検査し、同じポリシーを通す。
- 根拠: 承認UIを安全境界にしない。モデルが何を出してもモデル外で遮断する。
- トレードオフ: エージェントは画像を見られず、自分で描画して確かめられない。vork本来の自己修正ループより弱い。
- 受入条件: 自己テストのポリシー13件が通る。中止でclaudeプロセスが残らない。
- 未検証事項: `--tools ""` の隔離を敵対的に試していない。シーン内文字列による間接プロンプトインジェクション。

### D-05: final描画の承認を正確なシーンに束縛する

- 対象状態: 行動
- 変更前または現状: 描画はコマンド1行で、所要時間と上書きは実行後に分かる。
- 提案: 計画APIが版、シーンハッシュ、解像度、出力先、上書き有無、draftの実測時間、上限時間を返し、10分有効の承認チケットを発行する。描画APIはチケットとハッシュが一致しない限り403を返す。所要時間は予測せず、参考値として draft の実測だけを出す。
- 根拠: 承認したものと実行されるものを一致させる。架空のETAを出さない。
- トレードオフ: 小さいシーンでは過剰な手間。
- 受入条件: チケットなしで403。承認後に描画され、監査ログに `final_approved` と `final_rendered` が残る。
- 未検証事項: 長時間描画中の離脱と再開（現状はブラウザを閉じても描画は続くが、再接続UIはない）。

### D-06: 頻出操作は直接操作に置く

- 対象状態: 入力
- 変更前または現状: すべてを自然文で依頼すると、色を少し変えるだけで15秒以上と費用がかかる。
- 提案: 1つ選択したとき、メッシュは基本色・粗さ・発光、ライトは光量・色をスライダーとカラーピッカーで直接編集する。色はvorkの線形Rec.709とsRGBを変換する。
- 根拠: AIは例外的な依頼に残す。
- トレードオフ: 対応フィールドは5種類だけ。
- 受入条件: 非対応の組み合わせ（メッシュに光量など）をサーバーが拒否する。
- 未検証事項: 線形とsRGBの変換で利用者の色の期待と合うか。

### D-07: ADEモードでは、シーンを書くのはADEのエージェントだけにする

- 対象状態: 構成、入力、計算
- 変更前または現状: Director 内部の `claude -p` に、ADE で既に説明した内容をもう一度入力する必要があった（指示の二重化）。内部エージェントは描画画像を見ていなかった。
- 提案: `mcp.mjs`（stdio）が7ツールを公開する（director_status、vork_help、get_scene、propose_scene、get_render、wait_for_feedback、request_adoption）。propose_scene と get_render は描画PNGを MCP の image コンテンツで返す。人間のフィードバック（コメント、選択ノード名、表示中の版）は wait_for_feedback の long-poll（最大120秒）で届く。ADEモードでは内蔵 `claude -p` を呼ばない。
- 根拠: 指示系統を1本にする。エージェントが自分の描画を見て直せるようにする。
- トレードオフ: ADE側のエージェントの能力と権限設定に依存する。Codex は MCP ツールに承認が要るため、`default_tools_approval_mode` の設定が必要になる。
- 受入条件: 統合試験で7ツールの一覧、image コンテンツ、long-poll の早期復帰を確認する。Claude Code と Codex の両方で get_render の画像内容を説明できる。
- 未検証事項: 長いセッションでエージェントが wait_for_feedback を呼び続けるか。複数エージェントが同じプロジェクトに提案したときの順序。

### D-08: 採用は人間が承認し、画像とシーンをプロジェクトに残す

- 対象状態: 行動
- 変更前または現状: 採用した画像は Director の `runs/` に閉じており、アプリへの配置は手作業だった。
- 提案: エージェントは request_adoption で依頼だけを出す。人間が Director の承認画面で、書き込み先、上書きの有無、シーンハッシュ、final描画の要否を確認して承認する。画像を `<assetDir>/<slug>.png` に、シーン・ハッシュ・vork版・プロファイル・採用理由・PNGのsha256を `.vork/adopted/<slug>.json` に書く。採用の結果（パス）は wait_for_feedback でエージェントへ返る。
- 根拠: 画像の完成ではなく、アプリへの採用を完了条件にする。後日の修正のため、再生成できるシーンを残す。
- トレードオフ: Director を通さない書き込みは防げない（最大リスク参照）。
- 受入条件: 統合試験で sha256 の一致、上書き表示、使用済みチケットの拒否、プロジェクト外へのシンボリックリンクの拒否を確認する。
- 未検証事項: git管理下での差分の見え方。Next.js の画像最適化など、配信パスが変わる構成。

### D-09: ページ上で比べる

- 対象状態: 出力
- 変更前または現状: 判断材料は描画単体だけで、「単体できれい」と「ページに合う」を区別できなかった。
- 提案: `.vork/config.json` の `pageUrl` と `assetUrlPattern` を使い、headless Chrome で開発中のページを開いて、画像要求だけを候補PNGに差し替えたスクリーンショットを表示する（「On page」切替）。プロジェクトのファイルは変更しない。差し替え件数が0なら警告し、ページに接続できなければ理由を出して描画単体へ戻す。
- 根拠: 採用の判断を実画面で行う。
- トレードオフ: 開発サーバーが動いている必要がある。CSS背景画像や画像最適化URLではパターン指定に工夫が要る。
- 受入条件: E2Eで差し替え件数1以上、元ページとの差分、プロジェクトファイルの mtime 不変、0件時の警告、接続不可時の縮退を確認する。
- 未検証事項: レスポンシブ表示での複数幅比較（現在は1280×800のみ）。

## 6. 権限・承認・共有制御

- 計画を見せる条件: final描画（R2）。提案は計画の代わりに「解釈・前提・主張・実差分」を描画後に見せる。シーン編集は描画前に止める必要がない（R1、版として隔離済み）。
- 直前承認が必要な操作: final描画、プロジェクトへの書き戻し。
- 許可の範囲と期限: 1回、1版、1シーンハッシュ、10分。
- 拒否後の挙動: キャンセルで何も実行しない。サーバーはチケットなしの final を拒否する。エージェントに再試行させる経路はない。
- 一時停止・再開・中止: 中止は全ジョブで可能（子プロセスへSIGTERM）。一時停止と再開は未実装。
- 取消・補償操作: 採用の取消は旧版のHEAD化で行う（チェックアウトAPIあり、UIは未実装）。final の上書きは取り消せないため、計画画面で上書きを明示する。
- エージェントの権限（ADEモード）: エージェント用APIは `.vork/server.json`（パーミッション600）のトークンが必要。人間用API（採否、checkout、final計画、書き戻し、フィードバック送信）と描画ファイルは、ペアリング済みブラウザの HttpOnly・SameSite=Strict の Cookie が必要で、エージェントのトークンでは403になる。ペアリングは1回限りのトークンで行い、トークンは Director からOSのブラウザ起動コマンドへ渡すだけで、ファイルやログに書かない。MCP には採否・承認のツールがない。
- 境界の限界: 同じユーザー権限のエージェントは、`.vork/` の状態ファイルを直接書き換える、プロセスの引数を覗く、ファイルを直接置く、などで回避できる。この境界が防ぐのは、通常の手順で承認を代行することであり、敵対的な同一ユーザーのプロセスではない。強制にはADE側のサンドボックスが必要。
- モデル外の安全境界（単独モード）: 内蔵エージェントはツール・MCP・設定読込なし。シーンのファイル参照はサーバーで検査。サーバーは127.0.0.1のみで待受。Hostヘッダーを127.0.0.1/localhostに限定し（DNS rebinding対策）、POSTは同一Originと `application/json` を必須にする（CSRF対策）。`runs/` からは描画画像とIDマップだけを配信し、監査ログは配信しない。vork自体のサンドボックス化はしていない。
- 監査記録: init、proposed（依頼文、費用、警告数、経路）、agent_proposal_rejected、feedback、accept、discard、direct_edit、cancelled、final_approved（ハッシュ）、final_rendered、adoption_requested、adopted（ハッシュ、パス、sha256、上書き有無）、adoption_rejected、agent_error を `state.json`（単独モードは `runs/`、ADEモードは `<project>/.vork/`）に保存する。`node server.mts --report <project>` で、最初の提案から採用までの時間、フィードバック回数、破棄数を集計する。シーン全文とプロンプト全文はログへ入れず版ディレクトリに置く。

## 7. 信頼・倫理・アクセシビリティ

- 根拠と適用範囲: 露出統計は「vorkのメタデータ由来」と明記し、エージェントの主張と分ける。プロフィール（previs/draft/final）ごとに見え方が違うことを品質切替で示す。
- 不確実性の伝え方: 信頼度スコアは出さない。前提（assumptions）を一覧表示し、「説明ではなく画像で判断」と提案欄に記載する。実際にエージェントは「std/draftでは発光による間接光が弱い可能性」と前提を述べた。
- データ利用と記憶: 送信するのはシーンJSONと、利用者が選んだ文脈だけ。画像は送らない。セッションは永続化しない（`--no-session-persistence`）。版とログはローカルの `runs/` に残り、削除はフォルダ削除で行う。
- 異議申立てと救済: 個人を扱わないため対象が限られる。アセットのライセンスとクレジットは、vork README がクレジット保持を求めている点を踏まえ、外部素材を禁止することで現段階では回避している。
- 影響を受ける人: 素材の権利者（外部アセット禁止で回避）、生成画像を受け取る第三者（AI生成ラベルは未実装）。
- キーボードと支援技術: オブジェクト一覧のチェックボックスで画像クリックと同じ選択ができる。ジョブ工程は `aria-live` で通知し、エラーは `role=alert`。フォーカスは自動移動しない（例文と「この版から追加修正」を押したときの入力欄、final承認ダイアログの「Cancel」を除く）。スピナーは `prefers-reduced-motion` で止まる。
- 代替操作: 比較ワイプはスライダー（キーボード操作可）。色は数値も併記する。時間制限があるのはfinal承認チケット（10分）だけで、失効時は再計画できる。

## 9. 受入条件

| ID | 条件 | 検証方法 | 責任者 | 停止条件 |
|---|---|---|---|---|
| AC-01 | エージェント提案はHEADを変えず、採用操作でだけHEADが移る | E2E（提案→破棄でHEAD不変） | 実装者 | 提案がHEADを変えたら出荷停止 |
| AC-02 | 表示する差分はシーンJSONから計算される | 自己テスト（diff） | 実装者 | 自己テスト失敗 |
| AC-03 | 絶対パス・`..`・URLのファイル参照はvorkへ渡らない | 自己テスト（policy） | 実装者 | 1件でも通過したら停止 |
| AC-04 | final描画は承認チケットとシーンハッシュが一致した場合だけ実行される | API試験（403） | 実装者 | チケットなしで描画できたら停止 |
| AC-05 | キーボードだけで選択、依頼、採用、final承認まで完了できる | 手動キーボード操作 | 未定（アクセシビリティ担当） | 完了できない工程が1つでもある |
| AC-06 | 演出者が提案の誤りを画像比較で見抜ける | 5名程度の操作観察 | 未定（UXリサーチ） | 誤った提案の採用率が業務上許容できない |
